# Security and release verification

Merdeck operates beneath one explicitly configured project root with exact Host/Origin validation. Authentication is optional. With an access token, browsers sign in to bounded sessions and writes are CSRF-protected. Sessions are signed with a key derived from the runtime token and root, so they survive restarts until they expire; logout revocations are kept only in process memory, so rotate the token to sign out every browser after a suspected cookie leak. Without a token the service runs with open access: anyone who can connect can read, change, move and delete the Mermaid and Markdown files under the root. It then starts only when its bind address and every allowed origin are loopback, unless `MERDECK_OPEN_ACCESS=true` deliberately allows wider exposure. Loopback does not exclude other local users or connections forwarded by tunnels and proxies, so set a token on shared machines and wherever other people's connections are forwarded. Open access keeps root containment, file admission and the Host, Origin and fetch metadata checks that reject cross-site browser requests. Keep the root and runtime token outside release build inputs. Do not include real .env, cookies, operator projects or tokens in issue reports. Describe a security defect privately to the repository maintainer before posting exploitable details publicly; this project does not advertise a separate security service or disclosure address.

The source and compiled service preserve the same descriptor/path and optimistic-version checks. Linux/procfs and actual storage admission remain required. External tools retain direct file access. Known stale changes/deletion are rejected, but an uncooperative writer can change the file in the final comparison/rename window and be overwritten. Explorer file operations use the same containment and admission for every directory involved. They never replace an existing file or folder and never cross the root or another mount. Deletion is permanent, and an external write that lands between the final check and the unlink of a deleted or moved file can be lost in the same way. Local OS users able to move ancestors are outside the HTTP containment guarantee. The integrated policy admits only matching descriptor-verified overlay and ext4; unknown, tmpfs and the observed host-shared storage remain write-refused. Admission is not evidence of deployment readiness. Actual hosted ext4/Linux x64 source/executable acceptance passed at the exact candidate documented in README. This does not promise every mount configuration or remove the save/OS-actor limits.

Workflow checks use immutable verified action SHAs and read permissions. PR code receives no publishing credentials, and pull_request_target is not used. Only a version-tag publishing job receives contents:write through its standard GITHUB_TOKEN after actual native executable gates pass. It restores no writable caches and verifies tag/commit/version/inventory/digests before publication. Missing/mismatched existing release assets fail safely; no unrelated release/tag/asset is deleted. Failure uploads contain bounded redacted synthetic textual reports, never private configs, raw process traces, browser traces/video or arbitrary project contents.

Verify SHA256SUMS from the matching release before running the executable. These checksums establish attachment consistency; they are not an independent signature or protection against a compromised repository maintainer. No signing service or deployment account is introduced.
