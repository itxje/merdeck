# UPDATE-001 Detect deployed application updates safely

- **status**: completed
- **priority**: P2
- **owner**: Frontend maintainer
- **createdAt**: 2026-09-08

## Description

Identify the application build loaded in an open page, detect a replacement deployment and offer an explicit reload without losing any unsaved or recoverable work. Acceptance: an open page from an older build shows an update notice once the service serves changed frontend assets; reloading is possible only when no draft, dialog or pending action would be lost; the same build after a restart shows no notice; development pages never check.

## ActiveForm

Implementing application update detection on the main checkout.

## Notes

- 2026-09-08: claimed and proposed in [PLAN-010](../plan/PLAN-010.md) after the owner asked about open pages that keep running an old build. The first implementation on a separate branch passed its focused unit, API and real replacement checks, but its combined verification stalled on browser test process lifetime handling and a failed browser prerequisite installation, and it was never integrated. The branch is preserved locally under the `archive/update-001-wip` tag.
- 2026-09-11: the project owner asked to continue and finish this task. The branch predates the rename, file management and optional access tokens, so the feature is re-implemented on `main` as described in PLAN-010, reusing the design and tests of the first implementation where they still apply.
- Implementation (2026-09-11): `src/shared/application-build.ts` computes the identity (SHA-256 over sorted resource paths, content types and body digests, after removing the shell's `merdeck-build` element) and returns copied assets whose shell carries the element; applying it again yields the same identity and bytes. `scripts/build.ts` writes the element into `web/dist/index.html` after the frontend build, so the served shell, embedded assets and release inventories keep matching the build output. `src/app.ts` snapshots the served assets once and adds GET `/api/build` (`ApplicationBuild` in `src/shared/contracts.ts`), which needs no session and returns `identity: null` without a built interface. In the web app, `features/update/use-application-update.ts` reads the loaded identity from the shell and checks on load, every 60 seconds while visible and on focus, visibility or connectivity changes, with coalescing, a five-second event throttle and an isolated query client. `update-notice.tsx` shows the notice with **Reload application** and **Dismiss update**, and `reload-guard.ts` detects retained work in any file. `use-workspace.ts` keeps a synchronously updated draft reference beside its reducer, counts active saves, refuses new saves once navigation has started, and exposes `reloadBlocked` and `reloadApplication`. `workspace.tsx` places the notice below the header and also blocks reload while the file drawer or an entry, review or log-out dialog is open, or while a token is being typed. The browser spec `update.spec.ts` serves the first shell with an older identity, and the two renderer specs that list allowed request paths now include `/api/build`. Compared with the first implementation, the notice does not report failed checks on its own, the page's unload prompt is unchanged, and an in-flight session refresh does not disable reload.
- Pitfall: setting a `useState` value inside the draft dispatch callback triggers `react/set-state-in-effect` warnings wherever effects dispatch; keeping `useReducer` and updating a reference in the same callback avoids them.
- Verification (2026-09-11, main checkout, pinned Bun 1.4.2): `bun run check` passed inside the project tmux session with the supported overlay fixture parent under `/tmp` (`0x794c7630`) and the checkout `tmp/` as the refused parent (`0x65735546`). It ran 190 backend tests across 9 files (functions 98.89%, lines 99.51%), including the identity snapshot and build endpoint tests, plus the acceptance test and 187 frontend tests across 17 files (statements 93.95%, branches 88.82%, functions 91.21%, lines 94.31%), with lint, strict type checks and the production build. The built shell carried the identity of its 94 resources, and applying the snapshot again left its bytes unchanged. The full browser suite then passed 41 of 41 in 2.0 minutes, including both `update.spec.ts` cases.
- Real replacement (2026-09-11): two disposable deployments were prepared from that build, the second adding a CSS rule under a new asset name referenced from its shell. A page opened on the first showed no notice, still showed none after that same build restarted, and showed the notice once the second replaced it on the same origin. After **Reload application** the page carried the second identity, applied the new rule and showed no notice, with no page or console errors. A first attempt that changed a stylesheet in place kept the browser's cached copy after reload, which is why the check uses a new asset name, as real rebuilds do.
- Deployment and live evidence (2026-09-11): the hosted instance was relaunched from the main checkout in the `domain` window of the project tmux session with a build of the sources committed as `e5de951`. The previous service processes exited and the `merdeck` route disappeared before the relaunch. HTTPS `/api/health` returned 200 with service `merdeck`, and `/` and `/favicon.svg` returned 200. GET `/api/build` returned 200 with `Cache-Control: no-store` and the identity of the local build (`a29b92f07d80…`), which the live shell also carried, and POST returned 405. A real Chromium session on https://merdeck.example.test/ showed no notice for the current build. With its first shell rewritten to an older identity it showed the notice with reload enabled, and **Dismiss update** hid it, with no browser errors. Pages opened before this deployment cannot detect it and need one manual reload.
