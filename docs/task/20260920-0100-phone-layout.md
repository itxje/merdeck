# 20260920-0100-phone-layout Phone layout

- **status**: completed
- **priority**: P2
- **owner**: Frontend maintainer
- **createdAt**: 2026-09-20 01:00

## Description

Track 5 of the UI refresh proposal in `docs/plan/20260919-1736-ui-refresh-plan.md`: dock the AI file
editor to the bottom edge on phones instead of covering the document, start it closed under the
phone breakpoint without disturbing a desktop preference, collapse the no-provider state to one
dismissible line, move the theme switch, the assistant toggle and sign-out into a header overflow
menu, replace the top pane tab strip with a bottom bar holding the project-files control beside the
source and preview tabs, and raise every interactive control under the breakpoint to a 44px target.

- **relates to**: 20260919-1736-ui-refresh-plan (Track 5: Phone layout)

### A shared test helper conflicted with this track's own requirement

`web/src/test/e2e/support.ts`'s `login()` helper asserted the "Log out" button visible immediately
after authenticating, at whatever viewport the caller had already set. Moving sign-out into the
overflow menu below the phone breakpoint — this track's own explicit requirement — meant that
assertion failed for every spec that authenticates while already narrower than 700px, independent
of anything this track's own files changed afterward. `support.ts` was outside this task's original
file scope; reported rather than edited outside that scope, then brought into scope for the fix below.

Confirmed against the complete existing browser suite: this reached four cases already in the
repository, each authenticating while already narrower than 700px — one in `directory.spec.ts` and
all three in `drawer.spec.ts`. None were fixable from within their own files, since the failing
assertion ran inside the shared helper before the calling test regained control. Every case this
task added or extended instead authenticates at a wide viewport first and narrows afterward — the
same pattern the pre-existing, still-passing specs in this file already use — so none of this task's
own coverage ever depended on the fix below.

### Shared test helper fix (2026-09-20)

Replaced both of `login()`'s post-authentication assertions (the cookie-reuse path and the path after
the token fill) with a check for the project-files control, which is positive evidence that the
authenticated shell is present — unlike the absence of the sign-in form, which also holds on a blank,
error or failed-navigation page.

That control does not resolve to one stable element across every width, which the read-only survey
for the original track had not named: above 1100px the docked explorer itself is the control, an
`aria-label="Project files"` landmark; from 1100px down to the phone breakpoint and below it, the
control is the `aria-label="Open project files"` trigger that opens the drawer or the sheet. Measured
directly at 1440, 1100, 1099, 900, 700, 699 and 390px: exactly one of the two is visible at every one
of those widths, never both, never neither. `login()` now asserts a locator combining both forms with
`.or()`, so it holds at every width regardless of which of the two is the visible one there.

Confirmed sign-out is not losing coverage by moving: `workspace.spec.ts`'s existing narrow-viewport
case already opens the overflow menu, reads "Log out" by its exact accessible name, and carries the
confirmation dialog through to a real, completed sign-out at 390px — not merely a presence check, a
working sign-out reached through the menu. `header.spec.ts`'s narrow case separately asserts that
same button's touch-target size inside the menu. Between the two, reachability, accessible name and
functional completion under 700px are all covered; added nothing further.

Ran the four named cases (`directory.spec.ts`'s narrow-viewport case, all three in `drawer.spec.ts`)
against a rebuilt service after the fix: `login()` itself now succeeds at every one of them. One,
`directory.spec.ts`'s case, then failed slightly further in, on a second problem the `login()` failure
had been masking: a direct "Dark theme" click at 390px, unreachable there since it moved into the
overflow menu — the same shape of regression already found and fixed in three other specs during the
original round, just not visible in that one until `login()` stopped failing first. That fix
surfaced a third problem specific to this file: selecting a plain toggle inside the overflow menu
does not close it (it is not a menu item, so nothing tells the menu a selection happened), and the
menu's own backdrop then intercepts the pointer event on the very next click, on the "Preview" tab.
The other three specs never hit this because nothing they click after the theme toggle sits under
that backdrop. Added an explicit second click on the overflow trigger to close the menu before the
tab click; reran, passed. `workspace.spec.ts`'s own narrow case does not need the same addition: its
next interaction opens a modal dialog, which closes the still-open menu as an outside interaction on
its way in, and that already passed as recorded above.

Reran the complete existing browser suite with `MERDECK_TEST_AGENTS=true`, so the agent-gated cases in
`agent-editing.spec.ts`, `accent-contrast.spec.ts`, `header.spec.ts` and `type-scale.spec.ts` execute
rather than skip, against three services (token-protected and open-access, both with the same
scripted fake provider mirroring `scripts/test-e2e.ts`'s fixture, plus a tmpfs-backed
genuinely-unsupported-storage service). One run this way, on services already reused across several
prior rounds this same evening, reported two of `accent-contrast.spec.ts`'s cases and one of
`agent-editing.spec.ts`'s failing on an HTTP 429 from the open-access service — rate limiting
accumulated from reuse, not a product defect, the same shape already found and confirmed once during
the original round. Restarted the open-access service and reran those three cases alone: all three
passed. Restarted every service fresh and reran the complete suite once more end to end: 94 passed, 2
skipped (the Chromium-performance specs this run does not exercise), 0 failed — the four named cases
included, with the agent-gated cases actually executing rather than skipping.
