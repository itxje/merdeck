- **status**: completed

## Description

Track 5 of the UI refresh proposal in `docs/plan/20260919-1736-ui-refresh-plan.md`: dock the AI file
editor to the bottom edge on phones instead of covering the document, start it closed under the
phone breakpoint without disturbing a desktop preference, collapse the no-provider state to one
dismissible line, move the theme switch, the assistant toggle and sign-out into a header overflow
menu, replace the top pane tab strip with a bottom bar holding the project-files control beside the
source and preview tabs, and raise every interactive control under the breakpoint to a 44px target.

### Overflow menu backdrop, the trigger's touch target and the resize handle's range (2026-09-20)

Three defects, each with a failing reproduction added first and confirmed to fail against the source
at that point, then fixed in the product:

1. **Fixed: the overflow menu's controls did not close it.** The theme switch and the assistant
   toggle are plain controls rendered as the menu's children rather than menu items, so selecting one
   never told the menu a selection happened; it stayed open, and its full-viewport pointer layer
   intercepted the next tap anywhere else on the page, including on the bottom bar's own tabs. Made
   the menu controlled (`open`/`onOpenChange` in `workspace.tsx`) and closed it from one `onClick`
   handler on its content, which catches a completed click on any control inside — the theme switch,
   the assistant toggle, sign-out, a future addition, anything — without needing each one individually
   wired to know about the menu around it. Every control inside keeps its own accessible name and
   pressed or current state; only the surrounding menu's open state changes. Confirmed both named
   controls directly: toggling the theme and, separately, toggling the assistant from the menu each
   close it and leave the rest of the page responsive, reproduced live against a built service before
   this was recorded as fixed.
2. **The test-side workaround is gone, not kept beside the fix.** `directory.spec.ts`'s narrow case no
   longer clicks the overflow trigger a second time to force the menu closed; `overflow-menu-backdrop
   .spec.ts` (added as a failing reproduction, now passing) asserts the product behaviour directly —
   toggle the theme from the menu, then click the "Source" pane tab sitting behind where the menu was,
   and assert that tab actually became selected. A click landing on a real control behind the menu is
   the proof the backdrop is gone, not an inference from the menu's own state.
3. **Fixed, narrower than first attempted: the overflow trigger stayed under the 44px floor.** It
   wraps a `Button` through a `render` prop, and the wrapping primitive's own `data-slot`

   which the primitive has no reason to touch, unlike the styling slot it already overwrites.
   `.header-actions [aria-label="More options"] { min-height: 44px; min-width: 44px; }` in
   `index.css`, the file that already owns this floor; no shared primitive touched.
   - **Known issue, not fixed here:** the shared dialog's close button (`data-slot="dialog-close"`,

4. **The resize handle's reported maximum did not match what the layout could render.** The handle's

### The resize handle's maximum reinstated header height and read the device's safe area (2026-09-20)

An independent reproduction (`agent-safe-area-overlap.spec.ts`) showed the panel climbing up over the
header on a device that reports a nonzero bottom safe area. Tracing it back, the fix recorded above
for item 4 was itself already unsafe at zero inset: it capped the handle's range at a flat 85% design
ceiling together with the phone-bar-and-status-bar chrome, but dropped the header height from that
calculation entirely, so 85% of an 844px viewport (717.4px) left the panel's top edge at 40.6px —
above the 58px header — even before any safe area is considered. The `max-height` clamp that used to
backstop the panel's rendered height was removed in the same earlier change, so nothing else limited
the overshoot. Adding the safe-area inset on top of that ceiling, on its own, would not have closed
the gap: at a 34px inset the reachable room is still short of 85%, so the flat ceiling — not the
reachable room — would still have been the binding number, identical to the defect it was meant to fix.

The correction made at the time reinstated `headerHeight` as a permanent term in the same kind of
calculation, alongside the existing phone-bar-and-status-bar chrome, and read the device's own bottom
safe area live through a DOM probe instead of assuming it was zero — closing the specific gap the
reproduction above measured. That calculation was still a second copy of geometry the layout's own
CSS already renders, kept in step by hand rather than derived from it; the next round's independent
diagnosis found the copy was still short a term (the phone bar's own 1px border) and had no way to
react to an inset change that arrives with no resize event. Replaced entirely by the fix recorded in
the section below, which removes the copy rather than correcting another term in it.

### The panel's reachable height is now read from the layout, not reconstructed (2026-09-20)

Both corrections above computed the panel's reachable maximum as a list of numbers standing in for
boxes the layout already renders: a header height, a phone-bar-and-status-bar figure, and a probed
safe-area inset, combined by hand and kept in step with the actual CSS by hand. Every version of that
list was short a term at some point — first the header, then the inset, and a further independent
diagnosis found it was still short the phone bar's own 1px border, leaving the panel's bottom edge 1px
over the phone bar at every inset including zero. That overlap passed unnoticed because
`agent-editing.spec.ts`'s own geometry assertion carried a `+ 1` slack on exactly that comparison — a
tolerance for a real violation, not a rounding allowance. The safe-area inset compounds the same
problem a second way: the layout's CSS re-resolves `env(safe-area-inset-bottom)` on its own the moment
the value changes, with no event to observe, while the probed copy only refreshes on a `resize`, which
a safe-area change does not necessarily fire.

A reconstruction of a rendered geometry is one term short by construction: nothing keeps the list of
terms complete except remembering to update it every time the real layout gains or changes one, and
nothing catches a change that arrives without an event the copy happens to listen for. Fixed by
removing the second copy instead of correcting it again. Below the phone breakpoint, `.workspace-body`
becomes the containing block (`position: relative`), and `.agent-pane` is positioned against it
(`position: absolute`, `bottom: 0`, `max-height: 100%`) rather than offset by a computed distance from
the viewport edge — that containing block already begins under the header and already ends at the
phone bar in the normal layout flow, so the browser keeps the panel clear of both at whatever the
header, the bars and the safe area inset actually come to, with nothing to list and nothing to
observe. The resize handle's reported range is read back from that same box's own rendered height via
a `ResizeObserver` (plus a `resize` listener for the viewport-height denominator), rather than
estimated separately, so a header, bar or inset change is caught by the same observation that would
notice any other change to that box's size, with no separate signal to wire up. `headerHeight`,
`phoneChromeHeight` and the safe-area probe are gone from `agent-chat.tsx` entirely; `index.css` no
longer computes a bottom offset from those terms either.

The `+ 1` slack in `agent-editing.spec.ts`'s phone-layout assertion is removed now that the overlap it
was masking is gone. A new independent reproduction, `agent-panel-geometry.spec.ts`, asserts the
externally checkable property directly against real element geometry — the panel's top at or below the
header's bottom, its bottom at or above the phone bar, the status bar still reaching the viewport's
bottom edge — at a zero inset, at a nonzero inset present before the page loads, and with the inset
changed after mount with no resize following it (asserting the layout's own status-bar height already
grew, and counting `resize` events to confirm none fired). A control case first proves the reading
code against two figures known independently of anything the panel computes: the phone header's own
rendered height and the status bar reaching the viewport's bottom edge. `agent-handle-value-mismatch
.spec.ts` is kept rather than deleted: its assertion that the reported value tracks the reported
maximum is still true and still worth having, it is simply not sufficient alone to catch a shape
whose top edge covers part of the header, which is why the geometry case exists beside it rather than
replacing it.

Measured with the corrected layout, handle driven to its reported maximum, 390x844: at a zero safe-area
inset, the header's bottom edge and the panel's top edge both measure 58px — flush, no overlap — with
the reported value and maximum at 83, matching the rendered percentage. At a 34px inset, the header's
bottom edge and the panel's top edge again both measure 58px, with the reported value and maximum at
79. The three geometry cases above pass at both insets and across an inset change with no resize.

An independent lint pass on this candidate found one style violation in the new geometry spec — a
line combining two statements (setting a counter, then a nested listener body incrementing it) — and
flagged, without failing, a synchronous `setState` inside the `useLayoutEffect` that reads the
containing block's live height (`useReachableHeightPercent`'s `measure` function, called once directly
in the effect body). The style violation is fixed by splitting the listener body onto its own line;
no rule was silenced.

The synchronous `setState` itself is the correct shape for this measurement, not an oversight: the
value being measured — the containing block's rendered height — does not exist until after the DOM has
committed and the ref is attached, so it cannot be produced by a lazy `useState` initializer the way an
independently-computed value (like the safe-area probe elsewhere in this file) can; `useLayoutEffect`
plus a synchronous set is the standard way to read a just-committed layout and correct the state before
the browser paints, avoiding a visible flash of the wrong value. It cannot re-enter: the effect's own
dependency array is `[narrow, paneRef]`, neither of which the `setReachable` call touches, so the
state update cannot cause React to re-run the same effect. The subsequent calls to `measure` come only
from the `ResizeObserver` on the containing block and the window's `resize` event — genuine external
signals — and the state this effect sets never feeds back into the size of the box being observed: the
assistant pane is `position: absolute` inside that containing block, so its own height, which is what
`reachable` ultimately bounds, is taken out of normal flow and cannot affect the containing block's own
size. There is no path from this `setState` back to a resize of the element it observes.
