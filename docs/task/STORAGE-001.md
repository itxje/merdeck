# STORAGE-001 Evaluate write admission for host-shared virtiofs project storage

- **status**: completed
- **priority**: P2
- **owner**: Storage maintainer
- **createdAt**: 2026-09-12

## Description

The deployed instance reaches its configured project over a host-shared `virtiofs` mount (`statfs.type = 0x65735546`, mount record type `virtiofs`). Write admission accepts only overlay and ext4, so that deployment browses and previews every file but refuses every save with `filesystem_unsupported`. The project owner asked to evaluate admitting this filesystem family rather than leaving the deployment read-only. Acceptance: an investigation that records the exact mount, statfs and device identity of the storage under test; repeats the consecutive-save identity experiment from the [inode observations](../decisions/2026-09-07-inode-observations.md) on that mount with at least the same number of iterations, so the earlier failure class would be visible if it recurs; exercises each primitive the save protocol depends on there (`O_EXCL` creation, `link`/`unlink`, directory `rename`, `fsync`, and descriptor identity revalidation around the final comparison); states plainly whether the protocol's identity guarantees hold on that mount; and ends either with a proposal to admit the type under stated conditions or with a recorded refusal carrying its evidence. Admission itself does not change in this task: any change needs its own approved plan, and read-only browsing of unsupported storage stays as it is.

## Notes

- Context (2026-09-12): `writableFilesystem` in `src/modules/diagrams/filesystem.ts` requires Linux with procfs, a `statfs` type of overlay `0x794c7630` or ext4 `0xef53`, a uniquely associated mount record whose type string is `overlay` or `ext4`, a mount device matching the held descriptor's `stat` device, and the root, target and destination directory on one device. A `virtiofs` mount fails the type test twice, so `storageStatus()` reports `writable: false` and every save returns 503 before a temporary file is created. The allowlist exists because a host-shared mount produced two consistent reads of unchanged content with different inodes, which the save protocol uses to decide whether another writer replaced the file; that history is recorded in the inode observations decision and in [SAFETY-001](SAFETY-001.md). The question to answer is whether `virtiofs` shows the same behaviour or whether it can be admitted with the existing descriptor checks.
- Scope note: the evaluation covers the specific mount under test. A passing result on one host is deployment evidence for that host, not blanket support for the filesystem family, and each deployment still runs the documented acceptance against its own storage.
- Identity (2026-09-12): the storage under test is the mount that carries the configured project. A held directory descriptor beneath it reports `statfs.type = 0x65735546`, `stat` device 45, mount id 375, mount device `0:45`, mount point `/workspace` and mount type `virtiofs`. The procfs association the admission check depends on works there: the descriptor's `mnt_id` resolves to exactly one mount record and its major/minor pair matches the held `stat` device, so only the type allowlist refuses it. The control mount reports `0x794c7630`, device 55, mount id 366 and type `overlay`, and is admitted.
- Primitives (2026-09-12): a probe using built-in APIs only exercised every primitive the save and entry protocols depend on, and all nine behaved identically on the mount under test and on the control: exclusive creation refuses an existing name; hard link plus unlink moves a file without overwriting; directory creation, rename and removal; rename publishing over an existing target; directory `fsync` after publication; a descriptor anchor reporting the same identity as the anchored path; `O_NOFOLLOW` refusing a symlink; a hard-linked target remaining detectable through its link count; and an unlinked descriptor remaining observable.
- Identity stability (2026-09-12): a single publish cycle is stable. 120 in-process cycles plus 200 cycles across twenty separate processes published 320 of 320 with no identity mismatch, and a variant probe that isolated the absolute path, the descriptor anchor and the temporary file's metadata calls found no inode change in 600 cycles. Consecutive publication is not stable. Repeating the protocol's read, stage, re-read and rename cycle twenty times per fixture over twenty fixtures produced **7 mismatches in 400 cycles on the mount under test and 0 in 400 on the control**. Every mismatch has the same shape: identical bytes, identical size, and identical modification and change times to the nanosecond, with only the inode number different. The failure therefore appears only after a preceding atomic replacement in the same directory.
- Protocol effect (2026-09-12): with admission temporarily extended to this type in a throwaway checkout, and the file fixtures placed on the mount under test, the real file tests ran ten times over: 75 passed and 5 failed out of 80, all five in consecutive-save cases (`twenty consecutive multi-block save pairs preserve every surrounding byte` four times and `ordinary README contexts retain multiple byte-exact independently saved diagrams` once). An instrumented conflict branch confirmed the cause: the content version matched and the identity comparison failed, with equal size and equal modification and change times. The service therefore refuses roughly one in twenty saves on this storage with a false conflict. One storage CLI control also failed in that run, but for an unrelated reason: `scripts/check-storage.ts` refuses to run outside the project root and its session, which is an artifact of the throwaway checkout rather than a storage result. Evidence scripts and logs are under ignored `tmp/storage-001/`.
- Conclusion (2026-09-12): **the type stays refused.** The save protocol treats device and inode as the answer to "is this still the same file", and this mount does not keep an inode number stable across an intervening atomic replacement. The measured consequence is a fail-closed refusal, not a lost edit, but it makes saving unreliable at a rate an operator would notice. The experiment also does not establish the safe direction: a layer that can present a new number for one file can in principle present a reused number for another, which would make a genuine external replacement invisible, and nothing here rules that out.
- Follow-up options (2026-09-12), each needing its own approved plan: relax the identity model so it no longer depends on inode stability — the observed mismatches all had equal bytes, size and timestamps, so a comparison over device, size, modification and change time plus the content version would have accepted them, at the stated cost of no longer conflicting on a same-content external replacement; or keep the refusal and document the storage choices that do satisfy the current model for a deployment whose files arrive over a host share.
