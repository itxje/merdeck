## Structure

The root is a private Bun + Hono TypeScript API package. `web/` is an independent private React + Vite package, with its own manifest and lockfile. There are no workspaces, database, cloud account or remote hosting requirements.

```text
src/config.ts              validated explicit configuration and canonical root
src/app.ts                 typed Hono composition; domain mount and safe errors
src/index.ts               startup, listener and shutdown
src/modules/diagrams/      root-scoped tree, block extraction and practical atomic saves
src/shared/contracts.ts    API types and server-side request schemas
src/shared/errors.ts       safe domain errors and HTTP status mapping
web/src/app/routes/        file routes
web/src/app/routeTree.gen.ts generated and committed route tree
web/src/app/providers.tsx  Query, Theme and Tooltip providers
web/src/app/theme.tsx      light/dark/system preference and OS listener
web/src/shared/components/ui/ CLI-sourced base-nova primitives
web/src/shared/lib/http.ts same-origin request helper; type-only contract import
web/src/index.css          all semantic colors, light/dark and Tailwind mappings
web/src/features/          file tree, memory-only drafts, source and constrained preview
examples/project/          sample standalone and multi-block Markdown diagrams
designs/merdeck/        self-contained prototype; needs-review
tmp/                       ignored fixtures, server logs and browser evidence
```

## Configuration and containment

`loadConfig(environment)` reads no global environment itself. Startup injects one validated immutable configuration. `MERDECK_ROOT` is required, absolute, canonicalized once and checked for an accessible directory; there is no cwd default. `MERDECK_TOKEN` is optional; when set (an empty value counts as unset) it applies to every binding, including loopback, with 32–256 printable non-space ASCII characters. Generate random credentials; length validation does not prove entropy. Without a token the service runs with open access, which startup accepts only when the bind address and every allowed origin are loopback (127.0.0.0/8, `::1` or `localhost`) unless `MERDECK_OPEN_ACCESS=true`; that flag together with a token is rejected. Diagnostic errors identify invalid keys, never values or absolute paths.

Defaults: loopback `127.0.0.1:8787`, file size 1 MiB (maximum 8 MiB), tree 1,000 entries (maximum 10,000), depth 16 (maximum 32), 100 blocks per file (maximum 1,000), refresh 3 seconds (configurable 1–30 seconds), session lifetime 3,600 seconds (60–86,400), and at most 100 sessions (maximum 1,000). See `.env.example` for the exact keys. Domain and HTTP implementations must enforce these bounds, including UTF-8 byte length independently of the coarse request schema's character cap. HTTP request bodies must be bounded before JSON decoding; allow JSON escaping overhead up to six times `maxFileBytes` plus 8 KiB while still enforcing decoded file byte limits. Login bodies need only 4 KiB.

The file service alone performs project I/O. Every operation validates decoded root-relative POSIX paths, checks supported extensions, rejects symlinks and non-regular files and verifies component-wise containment. Transport schemas reject absolute paths, traversal segments, empty segments, control characters, backslashes, colon and literal percent characters. Percent-containing filenames are intentionally unsupported to remove double-decoding ambiguity. These schemas do not replace filesystem checks. Browser input cannot choose a root. No project directory becomes a static asset root.

## Public API contracts

Canonical exports are in `src/shared/contracts.ts`; frontend imports must be `import type`. Runtime schemas stay on the server. All responses use `ApiResult<T>`: `{ success: true, data }` or `{ success: false, error: { code, message, currentVersion? } }`. The following domain paths mount publicly under `/api`.

| Method and domain path | Request | Response data and semantics |
| --- | --- | --- |
| GET `/health` | None | `HealthStatus`; implemented, no filesystem/session details |
| GET `/build` | None | `ApplicationBuild`; identity of the served frontend build (`null` without one) and the 60-second check interval; no filesystem/session details |
| GET `/session` | Session cookie, if present | `SessionStatus`; false, true with `access: 'token'`, CSRF token and ISO expiry, or true with `access: 'open'`; authenticated statuses carry poll interval, source cap and storage eligibility |
| POST `/session` | `LoginRequest` JSON token; validated Origin | New bounded session cookie and authenticated `SessionStatus`; 405 with open access |
| DELETE `/session` | Cookie, Origin and `X-CSRF-Token` | `{ authenticated: false }`; revoke session and clear cookie; 405 with open access |
| GET `/diagrams/tree` | Authenticated session unless open access | `TreeSnapshot`; flat relative entries, detected block summaries, revision and truncation flag |
| GET `/diagrams/document?path=...` | `ReadDocumentRequest` | `DiagramDocument`; file kind, complete-file version and each selectable block's source |
| GET `/diagrams/revision?path=...` | `ReadDocumentRequest` | `DocumentRevision`; present with version, or deleted; no content |
| PUT `/diagrams/source` | `SaveDiagramRequest`, Origin; with a token also Cookie and CSRF token | Updated `DiagramDocument`; never create a missing file |
| POST `/diagrams/entries` | `CreateEntryRequest`, Origin; with a token also Cookie and CSRF token | `EntryChange`; creates a file from a fixed example template or an empty folder; never replaces an existing name |
| POST `/diagrams/entries/move` | `MoveEntryRequest`, Origin; with a token also Cookie and CSRF token | `EntryChange` for the destination; files need `expectedVersion` and keep their kind; never replaces an existing destination |
| POST `/diagrams/entries/delete` | `DeleteEntryRequest`, Origin; with a token also Cookie and CSRF token | `EntryChange`; files need `expectedVersion`; folders must be empty |

These endpoints are implemented. Health is intentionally public and reveals only service liveness. Session inspection/login are public authentication boundaries; every file/tree/revision/save request requires an authenticated session unless the service runs with open access. An unsupported route always remains a JSON error, including `/api` and `/api/*` in production; the SPA fallback never intercepts them.

A content version is a lowercase SHA-256 hex digest of the complete original bytes. A tree revision hashes a deterministic ordered representation of eligible entries, file versions, detected blocks, error states and truncation; metadata timestamps alone are insufficient. Polling must detect external edits even when timestamps are unchanged. Tree traversal and file hashing obey limits and may cache a bounded snapshot for no longer than the refresh interval.

Standalone `.mmd` and `.mermaid` files use `{ kind: 'standalone' }`. Markdown blocks use `{ kind: 'markdown', id: 'md:<ordinal>:<startByte>:<endByte>' }`: zero-based supported-block ordinal and UTF-8 byte content span, end exclusive. Identity is stable within the accompanying complete-file version only. A stale selector cannot retarget a different block because save compares `expectedVersion` before resolving the selector. `lineStart` and `lineEnd` are one-based source lines for presentation. Surrounding Markdown is never returned as renderable HTML. No-diagram Markdown has an empty `blocks` array.

Available file tree entries carry kind, version and block summaries without source. Unreadable, oversized and unsupported documents carry an explicit state, empty blocks and no invented version. `truncated: true` must be visible; omitted entries cannot be interpreted as deleted. Read/save of a vanished target returns `deleted` (410); the revision endpoint represents deletion as data. File operations report an existing destination as `exists` (409), a folder with contents as `not_empty` (409) and a missing destination folder as `not_found` (404). Conflict is 409, unsupported filesystem writes 503 (`filesystem_unsupported`), unsupported editing 415, too-large 413, invalid request 400, unauthorized 401, forbidden 403, missing route 404, method-not-allowed 405, unsupported-media-type 415, rate-limited 429, unavailable root 503 and unexpected internal error 500. `AppError` accepts fixed safe messages only. Conflict may include a current version but never file contents or absolute paths.

## Authentication contract

Authentication is optional. Without an access token the service runs with open access: GET `/session` reports `{ authenticated: true, access: 'open' }` with the same capabilities, POST and DELETE `/session` return 405, no cookie or CSRF token exists, and diagram routes need no session. Mutations still require the exact allowlisted Origin, and Host and fetch metadata validation still apply, so cross-site browser requests stay rejected; there is no ambient credential for a CSRF token to protect. Anyone who can connect can read and change files within the root, which is why startup accepts open access only for loopback-only services unless it is explicitly acknowledged.

With a token, the operator enters it through a same-origin login form. POST `/session` compares it in constant time, rate-limits failed attempts with bounded state, and exchanges it for a signed session. The cookie value is a random session id, the absolute expiry and an HMAC-SHA-256 signature over both and the issuing origin, under a key derived from the access token and the canonical project root; the CSRF token is derived from the session id under the same key. Sessions therefore survive a restart with the same token and root until they expire, and a new token or root signs every browser out. Process memory holds only the sessions issued by the running process, for capacity, and logout revocations until expiry. No persistent account or session store is required.

Cookie: `merdeck_session`, `HttpOnly`, `SameSite=Strict`, `Path=/api`, no Domain, bounded Max-Age, and Secure for explicitly configured HTTPS origins. It must retain the public `/api` path even when nsl strips the upstream prefix. Every mutation requires an exact allowlisted Origin; authenticated mutations also require the session-bound CSRF token in `X-CSRF-Token`. GET session returns that token to the same-origin page; it stays in memory. Validate Host against configured origins, reject cross-origin credentials and do not enable permissive CORS. Forwarded headers are untrusted by default; explicit origin configuration is required behind a TLS proxy. Credentials must not enter URLs, logs, client environment variables or persistent browser storage. Theme preference and the source/preview pane layout are the only persisted browser settings.

### Implemented HTTP security and lifecycle

`createApp(config, { diagrams, assets?, clock? })` composes one injected service; startup awaits service creation once. `app.close()` rejects new work and, when a token is configured, zeroes the session key and forgets issuance and revocation records. The listener gracefully drains requests on SIGINT/SIGTERM so an in-flight atomic save can finish. File handles are operation-scoped; there are no watchers, reconciliation loops or session-cleanup timers. Body readers have a 10-second total deadline with cancellation.

The login token and supplied secret are SHA-256 digested before constant-time comparison of fixed-length buffers. One process-wide bucket allows at most 10 login attempts per minute, including malformed or successful attempts. This avoids spoofable forwarded addresses and unbounded address maps; a login burst can temporarily throttle all users. Session capacity rejects sessions beyond the configured count issued by the running process with 429 and Retry-After rather than evicting active clients; sessions carried over from before a restart are not counted. Expiration is absolute, with lazy bounded cleanup of issuance and revocation records. New successful login rotates and revokes an existing cookie session; logout requires the current cookie, exact Origin and CSRF value and revokes the session in process memory, so a cookie copied before logout would verify again after a restart until it expires. Changing the access token revokes every session. Signatures bind sessions to their issuing configured origin, and a cookie in the earlier unsigned format reads as signed out.

Host and request URL authority must agree and match one exact configured origin. An Origin header, whenever present, must match that same origin. Mutations always require Origin; GET may omit it. Cross-site and same-site-but-cross-origin fetch metadata are rejected. Duplicate/malformed session cookies and unsupported Authorization headers fail closed. Forwarded and X-Forwarded-* values never affect Host, scheme, rate limits or session identity. The verified nsl proxy preserves the public Host and strips only /api, so no proxy bypass is needed. TLS reverse proxies must preserve Host and restrict direct upstream access; configure the public HTTPS origin explicitly. `MERDECK_COOKIE_SECURE=auto` derives Secure from HTTPS origins; `true` additionally requires HTTPS. Mixed HTTP/HTTPS origins, duplicate authorities and forced insecure cookies are rejected.

Authenticated SessionStatus adds `storage: { writable, filesystemType, supportedFilesystem: string }`. It also returns `maxSourceBytes: number` from the configured `limits.maxFileBytes` on login and authenticated inspection. This is the decoded UTF-8 source upper bound; complete-file Markdown framing and line-ending overhead can still trigger the authoritative server `too_large` response. Anonymous, expired and logout responses do not expose the cap. It reveals neither device identifiers nor absolute roots. Eligibility is advisory for the root; each save still validates the actual target and directory. An unavailable root prevents login completion without leaving a usable new session. Unauthenticated session status is exactly `{ authenticated: false }`. Open access reports the same capabilities with `access: 'open'` and neither a CSRF token nor an expiry.

JSON is uncompressed application/json, optionally charset=utf-8. Transport bounds streamed bytes before UTF-8/JSON parsing, checks declared lengths, rejects duplicate JSON keys and strict-schema unknown fields, and enforces decoded domain byte limits. Query decoding occurs once and rejects duplicate keys and malformed escapes. Requests also have an 8 KiB URL and 16 KiB aggregate application-header limit. Known routes enforce methods and return Allow plus typed 405; unsupported media returns typed 415. API and authentication responses use no-store and fixed safe errors. Server/runtime malformed HTTP rejection can occur before application dispatch; it never establishes a successful API response.

### Built page and asset boundary

Startup snapshots only the trusted web/dist build output into an injectable `StaticAssets` map. Compiled delivery supplies embedded bytes through the same boundary. Incoming requests perform exact map lookups, never filesystem resolution. The project root, source, environment files, symlinks and unexpected build file types are not served. The current frontend's only route is `/`, with selections in query parameters; `/index.html` also serves the shell. There is no fallback for unknown routes, `/api`, `/api/*` or missing assets. Only known `/assets/*` paths are served; assets have a conservative one-hour public cache lifetime while the shell is no-store. Stripped development mode serves no static assets and no duplicate /api mount.

All responses carry nosniff, no-referrer, DENY framing and same-origin resource policy. Production CSP permits same-origin scripts/connections/fonts, local or data images, and inline styles needed by the component and SVG renderers; it disallows inline scripts, external resources, frames, objects and base overrides. HTTPS origins additionally receive HSTS. The working shell, asset transport and constrained Mermaid renderer have real browser checks. Their observed scope and remaining native delivery gates are recorded below and in the task evidence.

## Files, polling and drafts

`src/modules/diagrams/` implements the file domain with built-in filesystem APIs and a pinned CommonMark parser for block context. Import `createDiagramService` and the `FileConfig` type from its index. Construct exactly one service with the validated `AppConfig`, then inject it into HTTP handlers. Its asynchronous methods return the existing shared contracts directly; HTTP wraps them in `ApiResult` and maps `AppError` using the existing safe mapper.

| Method | Result and behavior |
| --- | --- |
| `createDiagramService(config, options?)` | Validates the canonical root and supported host. Optional `clock` and repository lifecycle hooks are for deterministic local tests; never accept them from HTTP input. |
| `storageStatus()` | Fresh root filesystem eligibility and type/device metadata; unavailable roots remain typed errors. |
| `readDocument(path)` | Fresh `DiagramDocument`; validates paths, bytes and Markdown subset. |
| `saveDiagram(request)` | Updated `DiagramDocument` including newly computed selectors and whole-file version. Requires the original `expectedVersion` and selector. |
| `documentRevision(path)` | Fresh `DocumentRevision`; deletion is data, invalid/unsupported files and unavailable roots remain typed errors. |
| `createEntry(request)`, `moveEntry(request)`, `deleteEntry(request)` | `EntryChange` for the created, moved or deleted file or folder. They validate strict requests, share the save queue and invalidate the cached tree after success. |
| `treeSnapshot({ refresh?: boolean })` | Bounded `TreeSnapshot`; defaults to a defensive copy cached for at most `pollIntervalMs`. `refresh: true` bypasses the cache; overlapping scans coalesce. |

The repository validates root-relative POSIX paths again even when transport has validated them. It opens each directory component with `O_DIRECTORY | O_NOFOLLOW`, then accesses children through the held directory's `/proc/self/fd` anchor. Target reads use `O_NOFOLLOW | O_NONBLOCK`, descriptor metadata and regular-file checks. Root identity, canonical names, parent identity and target identity are revalidated around I/O. Symlinks, dangling links, hard-linked files and nonregular targets are rejected. Handles close at the end of each operation; there are no persistent handles or timers to dispose. Write admission requires **Linux with procfs, actual overlay/0x794c7630 or ext4/0xef53 mount identity, and the project root, target and destination directory on the same device**. The three eligibility sites pass their existing held FileHandles. The mount helper uniquely associates fdinfo mnt_id with a valid mountinfo record and compares its major/minor device to the held stat device. Missing/malformed/unassociated metadata or a mount/type/device mismatch refuses writes. Ext2/ext3 share 0xef53 but their mounted types remain unverified and refused. Twenty successful hosted raw controls at c1078e302cfe43eeaa8fc5bf9286a09273a74ee5 informed the ext4 correction; that first run failed the old admission gate. The corrected clean candidate 4ca471274d3ffa76469f8b2e87d4abd7055aa764 subsequently passed actual ext4/Linux x64 source and executable acceptance in run 34168525432. These are separate historical results. Unsupported hosts fail closed with `unavailable`. On Linux, other filesystems may be read subject to all existing containment checks, but every save fails with `filesystem_unsupported` (503) before temporary creation. The safe error asks the operator to verify write support for the configured project without suggesting relocation. No configuration can bypass this check. `storageStatus()` reports `{ writable, filesystemType, device, supportedFilesystem }` for the root; saves additionally enforce the actual held target/directory device and type. This metadata contains no absolute path. The supportedFilesystem string is a diagnostic policy label (currently linux-overlayfs,linux-ext4), not a client admission rule; writable remains authoritative. Each deployment must run the [documented acceptance](../README.md#file-storage-and-practical-acceptance) against its own selected storage; the tested overlayfs configuration does not establish blanket support for other overlay configurations, filesystems or operating systems.

Read-only document, revision and tree reads allow at most three complete attempts when internal consistency checks observe an unlinked descriptor or a changed current regular single-link target on the original device. Each attempt closes all target/directory handles before reopening and revalidating the root, ancestors, path, descriptor, links, size and returned bytes. Continued churn returns conflict; deletion retains its typed behavior. Public forbidden/conflict errors, permissions, hardlinks, symlinks, unavailable roots and write-side reads are not retry signals. The trusted read-open test hook only schedules actual descriptor events and never replaces metadata. Authentication and write admission/publication remain unchanged. See [PLAN-011](plan/PLAN-011.md) and [READ-001](task/READ-001.md) for baseline failures and bounded acceptance.

Saves and file operations serialize through one queue within this service instance, so a folder move cannot interleave with a save beneath it. Inside the critical section they read and compare SHA-256, resolve the selector, construct and validate replacement bytes, exclusively create a random hidden sibling at mode 0600, write and sync it, preserve original uid/gid and permission bits 0777, and re-read/hash the destination immediately before rename. Inode/size/mtime/ctime changes also conflict, including same-content atomic replacement. Deleted destinations are never intentionally recreated. The temp file is synced before rename and the directory after rename; cleanup unlinks only a temp entry still matching the descriptor created by that save. Existing BOM and all bytes outside the selected content span are retained. Special permission bits are removed; ACLs and extended attributes are not copied.

One service instance per trusted operator root is supported. External programs do not honor its lock. The final comparison and pathname rename are separate OS operations: an external write/delete between them can still be overwritten, and an actor able to move an already-open directory can move it beyond the approved root between revalidation and I/O. Descriptor anchors prevent symlink redirection to a different directory; they are not a sandbox against a hostile OS account or mount manipulation. Restrict root/ancestor mutation to trusted processes and use OS isolation for hostile users. Root identities also rely on filesystem inode/birth-time behavior. A post-rename directory-sync failure reports `unavailable` even though the replacement may already be visible; clients must reload/reconcile before retrying. No unconditional external-writer compare-and-swap or crash-durability guarantee is claimed.

### Open external-writer acceptance risk

**OPEN: the service can overwrite an uncooperative external write in the final comparison/rename window.** The explicit 2026-09-07 continuation accepts practical optimistic saving while preserving direct external editing. This exact counterexample remains a real limitation and its diagnostic interpretation remains `applicationSafetyPassed=false`; it is no longer a universal-no-loss gate for SAVE-001. The bounded reproduction is `bun tests/integration/files/external-writer-window.ts` using the pinned runtime in the project tmux session. It runs in an isolated process and intercepts only the final filesystem rename to schedule a separate real writer, which writes and syncs the destination before the real rename continues. No production save code or checks are bypassed or changed.

Observed result: the version at rename interception equals the supplied expected version; a different external content hash is then confirmed; the service returns success and its submitted bytes become the final file, replacing those external bytes. JSON evidence is in ignored `tmp/markdown-external-window.json`. The diagnostic exits zero when this counterexample is observed; that means successful reproduction of the risk, not successful no-lost-update acceptance. Its process-local module interception never runs inside the normal test gate.

The guarantees must remain distinct:

- Full-file version and identity checks reject changes already visible at those checks, including edits during temporary-file preparation.
- Per-file serialization ensures two service saves using a stale version cannot both overwrite one another inside one service instance.
- Uncooperative OS writers do not participate in that serialization and can change the file between the final check and rename. Their writes are not protected by a content compare-and-swap.

The built-in [filesystem rename API](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisesrenameoldpath-newpath) accepts source/destination paths, with no expected-content or inode predicate. Extra reads or synchronous calls can shorten a gap but cannot close it against another process. Exclusive temp creation protects only the new temporary name. Cooperative lock files/advisory locks cannot constrain unrelated editors. Rename flags such as no-replace or exchange also do not compare expected content; no-replace prevents updating an existing target, and exchange/rollback would require a different protocol with its own races. Backups can aid recovery but do not prevent replacement. No compatible built-in primitive was identified that supplies atomic expected-content replacement. The 2026-09-07 continuation retains the save protocol and this limitation. No force overwrite, exclusive-editor migration, database, native helper or staged-proposal workflow is introduced.

Verification also observed an unresolved inode-only change during a successive-save regression: identical content and timestamps, but a different inode caused the existing conservative check to reject the save. A finite six-case investigation reproduced it in isolated test processes and in a raw built-in filesystem sequence without the parser or test framework. Descriptor/path views agreed within each read, including birth time and link count, but differed across reads. Node and additional synchronous-stat controls did not reproduce the failure. A subsequently supplied direct acceptance control on overlayfs reported 40 passes and no failures with unchanged source and runtime; it was not rerun here. These negative observations do not establish the cause. See the [inode investigation](decisions/2026-09-07-inode-observations.md) for exact denominators, supplied-control provenance and remaining attribution gaps. No identity check or failing regression was removed. A passing individual run does not establish reliable acceptance or blanket filesystem support.

### Supported Markdown and lossless editing

Files must be valid UTF-8, with optional UTF-8 BOM, LF/CRLF newlines and no binary controls or lone carriage returns. `.mmd` and `.mermaid` provide one standalone block; `.md` provides zero or more selectable top-level Mermaid fences. Extensions and decoded language `mermaid` are case-sensitive. `mdast-util-from-markdown` 2.0.3 supplies CommonMark block context; only direct root-child `code` nodes with that language are candidates. The parser's one-based source lines are mapped onto the original buffer, never used as byte offsets or serialized back into Markdown. See the [compatibility decision](decisions/2026-09-07-markdown-context.md).

Ordinary prose, bullet/ordered lists, blockquotes, inline links, reference definitions, HTML sections and indented code can surround a valid top-level fence without excluding it. Nested list/blockquote diagram blocks are not selectable; the service does not traverse their descendants. Raw HTML, reference-definition content, indented code and non-Mermaid fenced code are never rescanned for inner-looking fences. CommonMark's actual block boundaries apply: a closing tag alone does not terminate HTML block types that require a blank line, and an indented fence after a list can remain nested despite a blank line.

Candidates must have explicit matching backtick/tilde closers, at least three opener characters, zero to three spaces of opener/closer indentation, a closer at least as long as the opener, and only spaces/tabs after the closer. Additional info words are allowed. Unclosed candidates and those requiring partial tab deindentation are individually omitted, preserving unrelated selectable blocks. A document containing only nested/unsupported candidates has an empty `blocks` array. The ordinal counts only selectable top-level blocks. File-level invalid text and configured size/block limits still produce typed errors; the surrounding document is not globally rejected for ordinary Markdown constructs.

Markdown selector offsets are UTF-8 bytes in the complete original file, including any BOM. They start immediately after the opener's newline and stop before the closing fence line. Sources include the content's trailing newline when present. A no-op save preserves original bytes exactly, including mixed indentation/newlines. Changed source uses the selected block's first existing newline convention (or opener newline), reapplies opener indentation, and ensures a nonempty Markdown replacement ends with a newline. A replacement capable of closing its enclosing fence is rejected; delimiters and other blocks are never rewritten. Standalone changes retain any original BOM and existing newline convention. Invalid Mermaid diagram syntax remains editable text for the renderer to diagnose; the file domain does not render or validate graph semantics.

### Discovery and revision limits

Discovery includes regular `.mmd`, `.mermaid` and `.md` files and ordinary directories. Hidden components and `node_modules`, `vendor`, `dist`, `build`, `coverage`, `secrets` (plus hidden tool/cache directories) are excluded from both discovery and direct access. Percent-containing names are intentionally unsupported. The traversal returns at most `maxTreeEntries`, descends only within `maxTreeDepth` (path-component count), visits at most eight times the configured entry limit, and hashes at most 32 MiB of file content per scan. The final file must fit the remaining byte budget before reading. Depth/work/byte exhaustion and inaccessible subtrees set `truncated: true`; this flag prohibits interpreting omitted files as deletions. A directory is sorted only within the bounded enumeration; a truncated subset is not a complete lexicographic page.

Tree revisions hash sorted relative entries, states, block summaries, complete readable-file versions and truncation. Readable binary/unsupported documents still contribute a private content digest to revision computation without exposing source or invented document versions. Same-size/same-mtime valid content changes, additions, removals and renames are detected on the next scan. Oversized/unreadable content cannot be hashed within the policy: changes within that unsupported state are not guaranteed observable until the file becomes readable/eligible. A scan is a bounded observation over time, not an atomic project-wide snapshot. Saved documents invalidate the tree cache, including scans started before the save. The service creates no watcher or interval; request-driven refresh uses the configured cadence (default 3 seconds), with an injectable clock for tests.

TanStack Query polls the bounded tree and selected-document revision at the server's interval, with no background-tab polling and no overlapping request per query. Reconcile on focus/reconnect/manual refresh; back off after failure and visibly show stale/disconnected state. There is no watcher, stream or event queue in the MVP contract. A rename is deletion of the old path plus creation of the new path. Cache invalidation follows a save. Clean drafts may reload automatically; dirty drafts remain separate from server snapshots and retain source on changes, deletion and navigation. Save completion marks only the submitted draft clean; subsequent typing remains dirty. Polling never authorizes overwriting a changed version.

## Development and production

`createApp(config)` mounts one domain router at `/api` by default. `MERDECK_API_MODE=stripped` mounts it at `/` only with `NODE_ENV=development`, for nsl's `/api` prefix removal. Tests verify both mount modes and API 404 JSON behavior. The dev launcher derives a unique name from the project path, allows a validated `MERDECK_DEV_NAME` override, discovers the real origin through `nsl get`, and runs API and Vite independently. Vite uses an explicit `NSL_PORT` CLI placeholder, loopback binding and its default localhost host allowlist. There is no committed Vite proxy or backend middleware import.

The build emits `web/dist/`, with its build identity written into the shell, and `dist/index.js` without rewriting source. Vite regenerates the committed route tree during development; production builds disable route generation. Commit generated route changes before checking/building. Production source delivery is `bun run build` then `bun run start` from the repository root containing both outputs. `/` and `/index.html` serve the workspace shell; exact built assets are served locally and unknown paths remain JSON 404. Downloadable delivery embeds these resources and the runtime/backend into one executable, with no separate assets or runtime installation. nsl is never a production dependency. Tests and long-running development processes use the project tmux session. Evidence remains in ignored `tmp/`; file acceptance explicitly selects a supported fixture parent as documented in README. API/UI/browser/binary checks must identify their actual fixture filesystem and preserve unsupported-root refusal. Fixtures are disposable samples; the product uses the operator's original configured directory directly.

## Design and rendering boundaries

CLI-owned primitives use shadcn/ui base-nova and Base UI exclusively. All colors are in `web/src/index.css`, including the dialog overlay token; component classes consume semantic variables. The separate draft reducer keeps a complete baseline document, its whole-file revision/selectors and individual block sources. Navigation retains scoped drafts, including missing-file drafts in a retained section. Clean documents refresh automatically. External changes preserve dirty baselines and show a warning; no force-save exists. A successful service save updates all offsets/revisions only when sibling baseline sources remain unchanged. Request generations, Query cancellation, selection-specific keys and a synchronous save guard prevent delayed responses or duplicate submissions from replacing newer work.

Revision and document observations carry structured warning origins. ### Constrained diagram preview

Rendering uses serialized Mermaid 11.17.2 calls with strict host configuration, root and flowchart HTML labels disabled, a 32,000-character preview limit and 500-edge limit. Exact bare `<br>`, `<br/>` and `<br />` label tokens (case-insensitive) are masked during global source validation and canonicalized to `<br/>` inside the private render call. Mermaid converts them to SVG text rows with HTML labels disabled; editor/draft/API/file bytes are never normalized. Attribute-bearing, malformed and encoded break forms remain rejected. Flowchart validation distinguishes double-quoted text, comments and complete newline/semicolon-delimited statements. Numeric or spaced comparison operators in quoted text and ordinary ampersand fan-out are supported. Complete classDef/class statements and inline class identifiers are validated before Mermaid can install CSS: identifiers use ASCII letters/underscore followed by word characters/hyphens; fill, stroke and color values are three/six-digit hex colors; stroke-width is positive and at most 10 pixels; stroke-dasharray has one to eight nonnegative lengths at most 100 pixels with at least one positive. Numbers use at most two decimal places with optional px. No other properties, selectors, escaped/encoded values or trailing declaration tokens are admitted. Source config/frontmatter directives, other HTML/entities, callbacks/links, Markdown resource links, arbitrary CSS, image shape metadata and math remain rejected before rendering. Other diagram families retain their conservative policy. This deliberately constrained subset can reject otherwise valid Mermaid; the source remains editable and savable. Larger source can also be saved within the service limit without preview. Each call resets the trusted configuration, skips obsolete queued work and never invokes renderer callback bindings. Subgraph containers take their fill, border and title colour from the dedicated `--diagram-cluster-bg`, `--diagram-cluster-border` and `--foreground` tokens, so they stay visible and neutral in both colour modes without altering node colours.

Generated SVG is sanitized using DOMPurify 3.4.15. The private measurement host supplies computed presentation values; final SVG removes style elements/attributes, active elements, links, images, external references and event attributes. Only constrained local marker/clip references survive. Mounted markup comes exclusively from that sanitizer; surrounding Markdown is never rendered. Serialized work plus selection/source cancellation prevents settings and delayed render results crossing diagrams. Syntax failure preserves the previous valid preview with an explicit stale label; empty source clears it. Geometry is measured after mounting, with a bounded viewBox and resize-aware fit, button zoom, pointer-anchored wheel zoom, drag panning and keyboard-focusable scrolling. Flowchart node labels can be located and edited from the preview: after a render settles, the serialized renderer parses the same source with Mermaid and tokenizes it with Mermaid's own flowchart lexer, mapping each rendered node's DOM id to the exact source range of the label Mermaid displays. An edit rewrites only that range, passes the unchanged source policy, and is accepted only if Mermaid parses the result as the same nodes, edges and groups with just that label changed; it then enters the ordinary draft flow. Markdown labels, other diagram types and anything the check cannot confirm stay source-only. Before the final sanitizer pass, node label text with less than 4.5:1 contrast against its node's solid fill switches to a dark or light neutral, so author class fills stay readable in both colour schemes.

The unit coverage gate measures handwritten state/data/render boundaries and the existing theme/HTTP helpers; sourced primitives and presentational composition are excluded. Real browser checks additionally exercise login, independent blocks, original Markdown bytes, edits during saving, external replacement/conflict/deletion, auth recovery, rendering safety, themes, dialog focus, desktop and 390 px layouts. The corrected hosted ext4/Linux x64 source and binary-only browser acceptance passed; historical local ARM64/overlay executable checks remain separately recorded in task evidence. The practical final compare/rename window and local OS actor limitations described above still apply.
